# Story 3.3: Dungeon Chest System for Equipment Overflow

## Status
Awaiting Manual Testing (Task 7)

## Story
**As a** player exploring dungeons,
**I want** to find hero equipment, reagents, and teeth in dungeon chests,
**so that** I can discover loot from previous hero deaths and benefit from the persistent world economy.

## Acceptance Criteria
1. Dungeon chests appear as interactive ASCII symbols (chest icon) in dungeon rooms
2. Chest interaction reveals contained equipment, reagents, and teeth with proper inventory management
3. Hero death distributes equipment, reagents, and teeth into chests using sequential filling logic
4. Chest contents persist in world state and can be discovered by any future hero
5. Visual feedback distinguishes unopened chests from opened/empty chests
6. Chests are created only on hero death or monster overflow (no random generation)
7. Existing chests are filled sequentially before creating new chests

## Background / Rationale

While Story 2.3 and 2.9 established basic chest functionality for death overflow (teeth and equipment from hero deaths), this story refines the chest system to support:
- **Reagent distribution** - Hero reagents are included in death overflow
- **Sequential chest filling** - Existing chests are reused before creating new ones
- **Persistent chest states** - Opened vs unopened visual distinction
- **Monster inventory overflow** - When monsters are over-equipped
- **Chest capacity limits** - Maximum 5 items per chest

This creates a cleaner, death-driven loot distribution system where chests serve as markers of previous failures. Equipment can be found through multiple paths: merchants (purchased), monsters (trophies), and chests (death overflow).

**Key Design Decision:** No random chest generation on level creation. All chests originate from hero deaths or monster overflow, reinforcing the game's persistent world economy where death shapes future gameplay.

### Extended DungeonChestRecord Interface

```typescript
interface DungeonChestRecord {
  id: string;
  pos: { x: number; y: number };
  items: EquipmentItem[];           // Equipment items only
  reagents: ReagentStack[];         // Reagent stacks (NEW)
  teeth: number;
  isOpened: boolean;                // NEW
  chestType: 'death' | 'overflow';  // NEW
}

interface ReagentStack {
  type: string;      // Reagent type (e.g., 'goblin_ear')
  count: number;     // Stack count (max 20 per stack)
}

const CHEST_CAPACITY = 5;  // Max total items (equipment + reagent stacks)
```

### Sequential Filling Algorithm

```typescript
function distributeDeathLoot(
  hero: Hero,
  levelDepth: number,
  existingChests: DungeonChestRecord[]
): DungeonChestRecord[] {
  const CHEST_CAPACITY = 5;

  // Separate equipment from reagents in hero.inventory
  // Equipment items don't have 'type' field or type !== 'reagent'
  // Reagents have type === 'reagent'
  const equipment = getEquippedItems(hero.equipment); // From hero.equipment slots
  const reagentItems = (hero.inventory as any[])
    .filter((item: any) => item.type === 'reagent') as ReagentItem[];

  const totalTeeth = hero.teethCurrency;

  // Find existing unopened chests with capacity
  const availableChests = existingChests
    .filter(chest => !chest.isOpened)
    .sort((a, b) => a.id.localeCompare(b.id)); // Oldest first

  const chests: DungeonChestRecord[] = [...availableChests];
  let currentChestIndex = 0;

  // Helper to get current chest capacity used
  const getChestUsedCapacity = (chest: DungeonChestRecord) => {
    return chest.items.length + chest.reagents.length;
  };

  // Distribute equipment first
  for (const item of equipment) {
    // Create new chest if needed
    if (currentChestIndex >= chests.length) {
      chests.push(createNewChest(levelDepth, hero.pos, 'death'));
    }

    const chest = chests[currentChestIndex];

    // Check capacity
    if (getChestUsedCapacity(chest) >= CHEST_CAPACITY) {
      currentChestIndex++;
      continue; // Try next chest (will create if needed)
    }

    // Add equipment to chest
    chest.items.push(item);
  }

  // Distribute reagents (with stacking)
  for (const reagent of reagentItems) {
    // Create new chest if needed
    if (currentChestIndex >= chests.length) {
      chests.push(createNewChest(levelDepth, hero.pos, 'death'));
    }

    const chest = chests[currentChestIndex];

    // Try to stack with existing reagent
    const existingStack = chest.reagents.find(r => r.type === reagent.monsterType);
    if (existingStack && existingStack.count < 20) {
      existingStack.count++;
      continue; // Stacked successfully
    }

    // Check capacity for new stack
    if (getChestUsedCapacity(chest) >= CHEST_CAPACITY) {
      currentChestIndex++;
      continue; // Try next chest
    }

    // Create new reagent stack
    chest.reagents.push({ type: reagent.monsterType, count: 1 });
  }

  // Distribute teeth evenly across all chests
  const teethPerChest = Math.floor(totalTeeth / chests.length);
  chests.forEach(chest => {
    chest.teeth = teethPerChest;
  });
  // Remainder teeth go to first chest
  chests[0].teeth += totalTeeth % chests.length;

  return chests;
}
```

### Chest Capacity Math

**Typical death scenario:**
- Equipment: 0-10 items (from Story 3.1's 10 equipment slots)
- Reagents: 0-10+ stacks (each unique reagent type = 1 chest slot, max 20 per stack)
- Teeth: Distributed evenly across all chests
- Chest capacity: 5 items (equipment + reagent stacks)

**Example 1:** Hero with 8 equipment + 3 reagent stacks = 11 total items
- Chest 1: 5 items (3 equipment + 2 reagent stacks)
- Chest 2: 5 items (5 equipment)
- Chest 3: 1 item (1 reagent stack)
- All 3 chests: Split teeth evenly (e.g., 100 teeth = 33, 33, 34)

**Example 2:** Hero with 4 equipment, level has 1 existing unopened chest with 3 items
- Existing chest: Filled to 5 items (3 old items + 2 new equipment)
- New chest 1: 2 items (remaining 2 equipment)
- Both chests: Split teeth evenly

### Bugfixes During Testing

**Bug: Opened Chests Disappearing After Deaths**
- **Reported:** User observed "some open chests persist, others don't, some stay longer than others"
- **Root Cause:** `distributeDeathLoot()` was filtering to only unopened chests and returning ONLY those, discarding opened chests from the level
- **Location:** `DeathProcessor.ts:65` - chest array only included `availableChests` (unopened)
- **Fix:** Preserve opened chests separately and return `[...openedNonEmptyChests, ...chests]`
- **Test:** Added test "should preserve opened chests when new death adds more chests"
- **Status:** ✅ Fixed and tested

**Enhancement: Refill Empty Opened Chests**
- **Design Decision:** User requested that empty opened chests should be refillable
- **Behavior:**
  - Empty opened chests (looted) are available for sequential filling
  - When refilled, they become **unopened** (isOpened = false) so player can loot again
  - Non-empty opened chests remain opened and are preserved
- **Implementation:** Filter includes `chest.isOpened && isEmpty`, then mark refilled chests as `isOpened = false`
- **Test:** Added test "should refill empty opened chests and mark them as closed"
- **Status:** ✅ Implemented and tested (16/16 tests passing)

**Bug: Async Response Error on Death**
- **Reported:** Console error "A listener indicated an asynchronous response by returning true, but the message channel closed before a response was received" when dying
- **Root Cause:** `worldState.saveWorld().catch(console.error)` calls were fire-and-forget (not awaited), causing IndexedDB transaction to close before saves completed
- **Location:** `main.ts:547` and `main.ts:603` (both after death events)
- **Fix:** Changed to `await worldState.saveWorld()` to ensure all saves complete before continuing
- **Impact:** Prevents potential data loss during death processing
- **Status:** ✅ Fixed and tested

**Bug: IndexedDB Boolean Index Query Error**
- **Reported:** Error "Failed to execute 'getAll' on 'IDBIndex': The parameter is not a valid key" during world state initialization
- **Root Cause:** Querying `isAlive` index with boolean values (`1` and `true`) is unreliable across browsers - IndexedDB doesn't consistently support booleans as index keys
- **Location:** `WorldState.ts:140-142` - `getByIndex(HEROES, 'isAlive', 1)` and `getByIndex(HEROES, 'isAlive', true)`
- **Fix:** Query all heroes with `getAll()` and filter in memory: `allHeroes.filter(h => h.isAlive)`
- **Impact:** More reliable, browser-agnostic, simpler code (no dual query workaround needed)
- **Performance:** Negligible - hero count is always small (1-2 heroes max)
- **Status:** ✅ Fixed and tested (400/400 tests passing)
