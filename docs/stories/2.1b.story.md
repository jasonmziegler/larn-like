# Story 2.1b: Town Hub, Multi-Level Dungeon & World Reset

## Status
Done

## Story
**As a** player,
**I want** a safe town starting area with a dungeon entrance, multiple dungeon floors connected by staircases that persist once generated, and the ability to reset the world for a fresh start,
**so that** I can explore progressively deeper dungeon levels across hero lifetimes in a persistent world, with a home base to return to.

## Acceptance Criteria
1. After naming a hero, the game starts in a town screen (static ASCII layout) instead of directly in the dungeon
2. Town contains a visible dungeon entrance tile (`>`) that the player walks onto and presses Enter (or walks into) to descend to Dungeon Level 1
3. Dungeon Level 1 contains a staircase up (`<`) that returns the hero to town, and a staircase down (`>`) leading to Dungeon Level 2
4. Each dungeon level N (for N >= 2) contains a staircase up (`<`) to level N-1 and a staircase down (`>`) to level N+1
5. Dungeon levels are generated on first entrance and persist in IndexedDB — revisiting a level shows the same layout, remaining monsters, and remaining items
6. The town layout is static (never regenerated) and persists in world state
7. On the Character Naming Screen, pressing Shift+Enter clears all world state (IndexedDB) and starts a completely fresh game
8. All persisted layouts (town + dungeon levels) survive browser refresh without change

## Dev Notes

### Existing Codebase Context

**Current game flow:**
```
TitleScreen → CharacterNamingScreen → initGame() → single dungeon level gameplay
```

**Target game flow:**
```
TitleScreen → CharacterNamingScreen → Town (depth 0) → Dungeon L1 (depth 1) ↔ L2 ↔ L3...
                                     ↑                        |
                                     └── staircase up ←───────┘
```

**Current file structure (relevant):**
```
apps/web/src/
├── game/
│   ├── Combat.ts           # Combat processing
│   ├── DungeonGenerator.ts # Level generation (rooms + corridors)
│   ├── Equipment.ts        # Equipment management
│   ├── Hero.ts             # Hero creation/stats
│   └── Inventory.ts        # Inventory management
├── world/
│   ├── WorldStore.ts       # IndexedDB CRUD layer
│   └── WorldState.ts       # State manager with save/load
├── ui/                     # UI screens (TitleScreen, CharacterNamingScreen, GameHUD, InventoryPanel)
├── main.ts                 # Game loop, state, rendering
└── (new files needed: TownGenerator.ts, LevelManager.ts)
```

**DungeonGenerator.ts** already returns `{ grid: DungeonGrid, rooms: Room[] }`. Staircase placement can use `rooms[0]` for up-staircase and `rooms[rooms.length - 1]` for down-staircase.

**WorldState.ts** already supports `saveLevel(level: DungeonLevelRecord)` and `getLevel(depth: number)`. The `DungeonLevelRecord` interface has `depth`, `dungeon` (grid), `monsters`, `items`, and `generatedAt`.

**CharacterNamingScreen.ts** handles keyboard input in its own `handleKeyDown` method. Shift+Enter detection: check `e.key === 'Enter' && e.shiftKey`.

### Staircase Tile Conventions
- `>` — staircase down / dungeon entrance (descend to deeper level)
- `<` — staircase up (ascend to shallower level / town)
- These are standard roguelike conventions (NetHack, Angband, original Larn)

### Town Design
Keep the town minimal for this story — a small enclosed area with floor tiles and a visible dungeon entrance. No NPCs, no merchants (those come in Epic 3, Story 3.2). The town exists purely as a safe zone and navigation hub.

Suggested town layout (~40x20):
- Walled perimeter
- Open floor area
- Dungeon entrance (`>`) near center or south
- Hero spawn point near north
- Future: merchant NPC location, shrine locations (reserved tiles not needed yet)

### Monster Spawn Rules
- Depth 0 (town): **No monsters**. Safe zone.
- Depth >= 1 (dungeon): Monsters generated using existing weighted distribution from `main.ts`. Scale monster count with dungeon area (existing logic).

### Level Transition Mechanics
When transitioning between levels:
1. Save current level state (grid, monsters, items) to WorldState
2. Load or generate destination level
3. Place hero at the arrival staircase position
4. Update `currentDepth` in GameState
5. Re-render with new level data

### Key Architectural Decision
The `DungeonLevelRecord` in `WorldState.ts` stores the full grid, monsters, and items. Town is just depth 0 with a simpler grid and no monsters. This means the existing persistence infrastructure handles town and dungeon levels identically — no special-casing needed in WorldStore.

### Testing

- **Test location:** `apps/web/tests/unit/game/`
- **Framework:** Vitest
- **IndexedDB mocking:** Use `fake-indexeddb` (already installed)
- **Pattern:** Follow existing patterns in `DungeonGenerator.test.ts` and `WorldStore.test.ts`
- **Key edge cases:**
  - Hero returns to town from dungeon level 1
  - Level 1 persists after visiting level 2 and coming back
  - World reset clears everything including multi-level data
  - Fresh game after reset generates new town and dungeon layouts

## Impact on Future Stories

### Stories That Benefit (No Changes Needed)
- **2.2 (Monster Promotion):** Now has "deeper levels" to promote monsters into — promotion logic can place evolved monsters on level N+1 which actually exists
- **2.4 (Death Site Teeth):** Teeth drops persist on the specific level where death occurred and are findable when hero returns
- **2.6 (New Hero Integration):** New heroes spawn in town and can choose when to enter the dungeon
- **4.1 (Procedural Generation):** This story implements 4.1's core AC5 ("Generated levels persist in world state and remain identical when revisited"). Story 4.1 can focus on generation quality improvements rather than the persistence + navigation infrastructure

### Stories That Need Minor Adjustments
- **2.2 (Monster Promotion):** Task 2 references "remove killer monster from current level" — this now means updating the specific `DungeonLevelRecord` for that depth, which is cleaner with LevelManager in place
- **3.2 (Town & Merchant):** Town screen now exists. Story 3.2 can add an NPC merchant to the existing town layout rather than creating town from scratch. Town generator should leave space for future NPCs
- **4.2 (Monster Population):** Monster count formulas should reference `depth` parameter for difficulty scaling. Current story places monsters uniformly; 4.2 can refine the distribution

### Stories That Can Be Simplified/Removed
- **4.1 (Procedural Generation):** Most of 4.1's infrastructure (persist on generate, load on revisit, depth 1-15 support) is delivered by this story. Story 4.1 can be rescoped to focus solely on generation algorithm quality (room variety, corridor styles, difficulty scaling) rather than the level management framework
